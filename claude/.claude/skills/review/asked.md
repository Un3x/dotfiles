# Asked versus built

Code review checks whether the change is sound; this pass checks whether it is the change that was asked for. A PR can pass every review round and still miss a behaviour the issue promised.

1. **Find the ask.** The PR body's `Closes` / `Suite de` link → the issue body in the project's tracker (read an issue, [`../tracker.md`](../tracker.md)), and the brief the project lead session gave when there is one. The PR body itself is a claim to verify, never a source for the checklist. No issue and no brief → skip the pass, write `Ask: no source found` in the report, nothing else.
2. **Write the ask as a checklist** before reading the diff: every behaviour the issue promises, every limit it states (« does not », « stays »), every acceptance line. From the issue's words, not the plan's: the plan is the author's reading, the same one the diff came from.
3. **Read the diff against the checklist**, one mark per line: **delivered** (the code does it; name the test or scenario that proves it when there is one), **missing** (nothing in the diff does it), **deviates** (done differently from what the issue says), **unclear** (the diff may cover it, say what would settle it). Then the reverse: **extra** — anything in the diff no line of the ask covers, with its size, and whether it crosses a stated limit.
4. **Check the user-facing lines.** When the project has a verify map (a `.claude/skills/` folder named `verify-<app>` or `<app>-verify`) and the diff touches routes, views or JavaScript, drive the mapped feature once and cite the evidence path; a screen the PR changes where it should stay the same is driven once more on the default branch, that screen only, for its « before » capture: after the PR drive, in a `git worktree add` of the default branch in the scratchpad, driven with the PR checkout's verify map (a local map stays out of a worktree), never a checkout under the running specialists, the worktree removed once captured; without a map, cite the system test that walks the path. A line the review could not check this way stays `delivered` when the code delivers it, and the report's `Note:` says the review could not check it: the review's limit, never a gap of the PR.
5. **Verdict**: `delivered` (every line delivered, no deviation), `partial` (missing or unclear lines), `off-target` (a deviation, an extra that crosses a stated limit, or an extra larger than the ask). The verdict goes on the report's `Ask:` line. Each missing, deviating or unclear line and each limit-crossing extra is an `ask` finding, ranked as [`output.md`](output.md) § Severity says; delivered lines stay off the report.
